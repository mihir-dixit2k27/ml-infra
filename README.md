# Telco Churn MLOps Pipeline

Welcome to the Telco Churn MLOps project! This repository contains a fully containerized, end-to-end Machine Learning Operations (MLOps) pipeline designed to predict customer churn. It demonstrates how to take a machine learning model from a simple training script to a production-ready, monitored, and automated system.

## 🚀 Project Overview

The core goal of this project is to predict whether a telecom customer is likely to churn (cancel their subscription). But instead of just a Jupyter notebook, this is a complete system that:
1. **Trains** a Random Forest model and tracks its performance.
2. **Serves** the model via a REST API for real-time predictions.
3. **Logs** live prediction requests and data to a database.
4. **Monitors** the incoming live traffic for data drift (i.e., when real-world data starts looking different from the data the model was trained on).
5. **Automates** retraining the model using Airflow when drift is detected.
6. **Visualizes** everything on an interactive dashboard.

## 🛠️ Architecture & Tech Stack

This project is orchestrated using **Docker Compose** and relies on several key open-source tools:

* **MLflow:** Used for experiment tracking and as a Model Registry. It keeps track of model versions, training metrics (like accuracy and F1 score), and artifacts.
* **FastAPI:** Powers the prediction API. It dynamically loads the latest "champion" model from MLflow and serves predictions while logging all incoming feature data and predictions to PostgreSQL.
* **PostgreSQL:** The central database. It stores MLflow's backend data, Airflow's metadata, and the live prediction logs (`prediction_logs` table) generated by the FastAPI service.
* **Apache Airflow:** The orchestrator. It runs scheduled DAGs to monitor data drift and trigger model retraining when necessary.
* **Streamlit:** A real-time observability dashboard that connects to both MLflow and Postgres to visualize live traffic, monitor data drift, and compare model performance.

## 📂 Repository Structure

* `api/`: Contains the FastAPI application (`simple_api.py`) and model loading logic.
* `src/`: Houses the core Python scripts for the ML lifecycle, such as `train.py` (model training pipeline), `drift_monitor.py`, and `send_traffic.py` (for simulating live API requests).
* `dags/`: Contains Apache Airflow DAGs (`drift_check.py`, `retrain_model.py`) that define the automation workflows.
* `dashboard/`: The Streamlit application (`app.py`) for visualizing system health, traffic, and drift.
* `data/`: Directory for storing processed training and validation datasets.
* `docker-compose.yml`: The blueprint that spins up the entire infrastructure (Postgres, Airflow, MLflow, FastAPI, and Streamlit).

## 🔄 How It All Works Together

1. **Training & Registration:** Running `src/train.py` trains a model on the data in the `data/` folder. The model pipeline (including preprocessing) is saved and registered in MLflow under the name `telco-churn-champion`.
2. **Serving:** The FastAPI container (`api`) boots up, talks to MLflow, and loads the production model. It exposes a `/predict` endpoint.
3. **Logging:** Whenever a prediction is requested, the API returns the result and seamlessly saves the input features and the prediction to the Postgres database.
4. **Observability:** You can open the Streamlit dashboard to see how many predictions are being made, what the overall churn rate looks like, and view historical model performance.
5. **Drift Detection:** Airflow periodically checks the recent live data in Postgres against a baseline. If the data distributions shift significantly (e.g., customers suddenly have much higher monthly charges), a drift alert is triggered.
6. **Retraining:** Once drift is detected, Airflow can automatically trigger the `retrain_model_manual` DAG to train a fresh model, which FastAPI will subsequently pick up.

## 🏁 Getting Started

To spin up the entire ecosystem, ensure you have Docker and Docker Compose installed, then simply run:

```bash
docker-compose up --build
```

Once the containers are healthy, the services will be available at:
* **Prediction API (FastAPI):** `http://localhost:8000/docs`
* **MLflow UI:** `http://localhost:5001`
* **Airflow Webserver:** `http://localhost:8080` (Default login: admin / admin)
* **Streamlit Dashboard:** `http://localhost:8501`

## 🧪 Step-by-Step Testing Guide

Follow these steps to observe each component of the MLOps pipeline working individually and together:

### Step 1: Verify MLflow (Model Registry)
- Open your browser and navigate to: **http://localhost:5001**
- **What to check:** Ensure the UI loads. If the model was trained successfully during startup, you should see the `Telco_Churn_Champion` experiment and the registered model.

### Step 2: Verify FastAPI (Model Serving)
- Run this command in your terminal to check the API health:
  ```bash
  curl http://localhost:8000/health
  ```
  *(It should return `"status": "healthy"` and confirm the database is connected).*
- Open your browser to: **http://localhost:8000/docs** to see the Swagger UI.

### Step 3: Simulate Normal Traffic
Let's send some realistic user data to the API to make sure it's predicting and logging properly.
```bash
python src/send_traffic.py --mode normal
```
- Let this run for about 10-20 seconds to generate logs, then press `CTRL+C` to stop it.
- **What to check:** The terminal should show successful predictions.

### Step 4: Verify the Streamlit Dashboard
- Open your browser to: **http://localhost:8501**
- **What to check:** Go to the **"Live Traffic"** tab. You should see the total number of predictions you just generated, along with the pie chart of the churn distribution. 

### Step 5: Simulate Data Drift (The "Attack")
Now, let's intentionally send skewed data (e.g., extremely high tenure, impossible charges) to trigger the drift alarm.
```bash
python src/send_traffic.py --mode drift
```
- Let this run for about 15-30 seconds to skew the database statistics, then press `CTRL+C`.
- **What to check:** Go back to the Streamlit Dashboard and click the **"Data Drift"** tab. Select `TotalCharges` or `tenure`. You should see a giant red alert saying **"🚨 DRIFT DETECTED!"** because the live traffic no longer matches the baseline training data.

### Step 6: Verify Airflow & Automated Retraining
Now that drift has occurred, Airflow should catch it and trigger a new training run.
- Open your browser to: **http://localhost:8080**
- Log in with username: **`admin`** and password: **`admin`**.
- Click the **"Play"** button (▶️) on the `drift_check_daily` DAG to trigger it manually.
- **What to check:** 
  1. Click into the DAG. You will see it run the drift check script.
  2. It will query the database, realize drift occurred, and branch into `retrain_model_task`.
  3. Go back to MLflow (**http://localhost:5001**), and you will see a brand new model version has been logged and registered!
